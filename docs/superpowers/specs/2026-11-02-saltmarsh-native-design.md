# Saltmarsh Isles: native Apple app with AI seats, design

Approved 2026-11-03. The implementation plan that follows from this design is in `docs/superpowers/plans/2026-11-02-saltmarsh-native-plan.md`.


## 1. Intent

Rebuild the `saltmarsh.html` prototype as one SwiftUI app that runs on iPhone, iPad and Mac, then add AI opponents so one person can play alone. The HTML prototype has already proved the rules and the screen flow. The native app keeps that flow, closes the four rule gaps the prototype left open, and lets each seat be a human or an AI with a chosen effort level.

Why native: AI opponents need a pure rules engine they can search over, the game needs to survive the app closing, and the owner wants to install it on their own devices.

The existing files `saltmarsh-isles-spec.md` and `saltmarsh-isles.feature` describe the prototype. Both get updated to describe the native app. `saltmarsh.html` is left alone.

## 2. Goals, non-goals, anti-goals

**Goals**

- Every rule in the spec, plus the four gaps: trading between players, bank supply limits, roll for first player, piece limits.
- Any seat can be Human or AI. AI seats have five effort levels from careless to strong.
- The AI never sees hidden information and never bypasses the engine.
- The Gherkin feature file is executed directly by the test suite.
- A game survives quitting the app (autosave and resume).
- One codebase, three device families, with the layout adapting (board beside panel on iPad and Mac, board above a scrolling panel on iPhone).

**Non-goals**

- Online or networked play.
- Language-model table talk, coach mode, or any network AI.
- App Store assets beyond a basic icon and bundle identifier.
- Changes to `saltmarsh.html`.

**Anti-goals** (would make this a failure even if it ran)

- An AI that reads opponents' hands or the deck order.
- An AI turn that freezes the interface or runs for more than a couple of seconds per decision on a phone.
- The spec, the feature file and the app disagreeing with each other.

## 4. Architecture

Four layers, each a separate Swift target so the dependency direction is enforced by the compiler. Everything except the views and the on-disk store lives in a Swift package, so the whole feature file runs under `swift test` from the command line.

```
SaltmarshIsles/                     (repo root, existing files stay)
├── Package.swift                   SaltmarshCore package
│   ├── Sources/SaltmarshEngine/    pure rules, no UI, no Foundation UI types beyond CGPoint
│   ├── Sources/SaltmarshAI/        depends on Engine only
│   ├── Sources/SaltmarshGame/      depends on Engine + AI: GameViewModel (@Observable), ScreenState,
│   │                               TurnRunner (AI pacing), GameStore protocol (persistence)
│   ├── Sources/ai-bench/           opt-in executable: level-vs-level matches at shipped budgets
│   └── Tests/
│       ├── EngineTests/            unit + property tests
│       ├── AITests/
│       └── GherkinTests/           parser, step definitions, runs ../saltmarsh-isles.feature
├── App/                            SwiftUI app target (generated by XcodeGen from project.yml)
│   ├── SaltmarshIslesApp.swift     entry point, wires FileGameStore + real pacing into GameViewModel
│   ├── Views/                      BoardView (Canvas), panels, sheets, victory overlay
│   └── FileGameStore.swift         GameStore backed by Application Support
├── AppUITests/                     XCUITest: launch smoke tests + the @ui-tagged scenarios
├── project.yml                     XcodeGen definition: multiplatform app + UI tests, links SaltmarshCore
└── docs/superpowers/               specs and plans
```

**Engine** is a value-type state machine. `GameState` is `Codable` and `Equatable`. `Engine.legalMoves(state)` returns every legal `Move`; `Engine.apply(move, &state)` mutates or throws. All randomness goes through a seedable generator stored in the state, so a game is replayable from its seed and move list. The UI and the AI both go through `apply`. The Engine also owns the two functions that cross the hidden-information line: `Engine.view(state, for: seat) -> PlayerView` (redaction) and `Engine.sampleFullState(from: PlayerView, using: &rng) -> GameState` (a guessed full state built only from public facts, for search).

**AI** receives a `PlayerView` (see section 6) and the legal move list, returns one `Move`. It also answers trade offers. The live `GameState` never enters this target. For search the AI asks the Engine for guessed full states and drives those through `apply` and `legalMoves`.

**Game** holds the view model, which owns the state, runs AI turns through `TurnRunner` (pacing is injected: real delays in the app, zero in tests), applies their moves, saves through the `GameStore` protocol (in-memory store in tests), and derives `ScreenState` for the views and the Gherkin steps.

**App** is views plus the file store plus the entry point. No rules, no AI, no test-relevant strings live here.

### 4.1 State model

Extends the spec's section 4 model. Additions in bold.

```swift
enum Resource: String, CaseIterable, Codable { case timber, clay, wool, grain, ore }
enum Terrain: Codable { case land(Resource), desert }
enum DevCardType: String, Codable { case knight, victoryPoint, roadCrew, bumperHarvest, cornerMarket }

enum Seat: Int, Codable { case crimson, cobalt, amber, ivory }   // fixed names and colours

enum Controller: Codable { case human, ai(EffortLevel) }          // NEW
enum EffortLevel: Int, Codable, CaseIterable { case deckhand = 1, sailor, mate, captain, admiral }  // NEW

struct Player: Codable {
    var seat: Seat
    var controller: Controller                                    // NEW
    var hand: [Resource: Int]
    var devCards: [DevCard]
    var knightsPlayed: Int
}

struct TradeOffer: Codable, Equatable {                           // NEW
    var proposer: Int
    var give: [Resource: Int]      // at least 1 card, all held by proposer
    var want: [Resource: Int]      // at least 1 card, no resource appears on both sides
    var to: Int?                   // nil = everyone else
}
enum TradeResponse: Codable, Equatable { case pending, accepted, declined, countered(TradeOffer) }  // NEW

enum Phase: Codable, Equatable {
    case rollingForFirst(rolls: [Int?], contenders: [Int])        // NEW
    case setup(step: Int, placingRoad: Bool, lastSettlement: Int?)
    case awaitingRoll
    case discarding(queue: [Int])                                 // seat indexes still to discard, in seat order
    case movingRobber(returnTo: Phase)                            // what to resume: awaitingRoll (knight before roll) or main
    case choosingVictim(candidates: [Int], returnTo: Phase)
    case placingFreeRoads(remaining: Int)
    case main
    case tradeOffered(offer: TradeOffer, responses: [Int: TradeResponse])   // NEW
    case gameOver(winner: Int)
}

struct GameState: Codable, Equatable {
    var tiles, corners, edges, harbours
    var players: [Player]
    var firstPlayer: Int                 // NEW: seat index that won the opening roll; turn order is seat order starting here
    var current: Int
    var turn: Int
    var robberTile: Int
    var dice: [Int]?
    var bank: [Resource: Int]            // NEW: starts at 19 each
    var devDeck: [DevCardType]
    var devCardPlayedThisTurn: Bool
    var longestRoadHolder: Int?
    var largestArmyHolder: Int?
    var phase: Phase
    var log: [String]
    var rng: SeededRNG                   // NEW: Codable, so replays and saves are exact
}
```

`Phase` is `indirect` (it nests itself in `returnTo`). The AI uses its own `SeededRNG` for search so a search never consumes the game's dice stream; the game stays replayable from its seed and move list regardless of how much the AI thinks.

Piece counts are derived, not stored: settlements = corners owned and not city, cities = corners owned and city, roads = edges owned.

### 4.2 Moves

```swift
enum Move: Codable, Equatable {
    case rollForFirst                                   // NEW
    case placeSettlement(corner: Int)
    case placeRoad(edge: Int)
    case upgradeCity(corner: Int)
    case roll
    case discard([Resource: Int])                       // NEW as a move (was UI state); exactly half, rounded down
    case moveRobber(tile: Int)
    case steal(from: Int)
    case bankTrade(give: Resource, get: Resource)
    case harbourTrade(harbour: Int, give: Resource, get: Resource)
    case proposeTrade(TradeOffer)                       // NEW
    case respondToTrade(seat: Int, TradeResponse)       // NEW: accepted / declined / countered
    case executeTrade(with: Int)                        // NEW: proposer picks one accepting seat or one counter
    case withdrawTrade                                  // NEW
    case buyDevCard
    case playKnight
    case playRoadCrew
    case playBumperHarvest(Resource, Resource)
    case playCornerMarket(Resource)
    case endTurn
}
```

`legalMoves` enumerates finite choices fully (all corners, edges, tiles, 20 bank trades, 15 bumper pairs, 5 market resources, all discard combinations when the count is small, else a representative set). For `proposeTrade` the offer space is unbounded, so `legalMoves` lists a bounded canonical set (every offer with up to 2 cards on each side that the proposer can pay) and `apply` validates any offer the UI constructs. A separate `Engine.validate(offer, state)` exists for the UI to gate the Offer button.

`legalMoves` is the single source of truth for which corners glow, which edges dash, and which buttons are enabled.

## 5. Rules

Everything in `saltmarsh-isles-spec.md` section 1 stands, with these additions and changes.

### 5.1 Roll for first player

Before setup, every seat rolls two dice once, in seat order. Highest total goes first. Seats that tie for highest re-roll among themselves until one is highest. Human seats tap "Roll for first"; AI seats roll after the usual pacing delay. The log records each roll.

Turn order is then seat order starting from the winner (e.g. Amber wins in a 3-player game: Amber, Crimson, Cobalt). Setup snake order starts from the winner too. Seats keep their fixed colours and scoreboard positions.

An order strip above the board shows the placement order during the first-player roll and during setup, highlights whose placement is next, and reads "Round 2: reverse order" during the second half of the snake.

### 5.2 Trading between players

Allowed on the current player's turn, after rolling, whenever `main` phase actions are allowed. Repeatable.

**Proposing.** The current player builds an offer: a give side and a want side (steppers per resource), and a target: everyone or one seat. Valid when give and want each hold at least one card, no resource is on both sides, and the proposer holds the give side. Tap "Offer".

**Responding.** The phase becomes `tradeOffered`. Each targeted seat answers:

- An AI seat answers at once: accepted (only if it holds the want side), declined, or countered with a changed offer it would accept. The AI judges offers with the same position evaluator it uses for moves; see section 6.
- A human seat is handed the device: the panel takes on their colour, header "<Name> · trade offer", and shows "<Proposer> offers <give> for <want>" with Accept and Decline. Accept is disabled with "You don't have <want>" when they can't pay. Their own hand is shown in the hold so they can judge the offer (owner's decision, 2026-11-05). Human seats cannot counter on screen (owner's decision: they say it aloud and the proposer edits the offer). Human responders are asked one at a time in seat order; the status line says who the device goes to.

**Closing.** When every response is in, the panel returns to the proposer and lists each seat's answer. The proposer taps "Trade with <Name>" on an acceptance or a counter, or "Withdraw". Executing a counter means the proposer accepts the counter's terms. Exactly one trade happens per offer. Cards move between the two hands; the bank is not involved. The log reads "<A> traded <give> with <B> for <want>." or "<A> withdrew the offer."

**AI proposing.** An AI seat may propose on its turn. Human seats see the same Accept/Decline prompt. After the responses the AI decides execute or withdraw through the same `Opponent` call.

Any player with an empty hand is skipped as a responder. Opponents cannot trade with each other during someone else's turn.

### 5.3 Bank supply

The bank starts with 19 of each resource and is shown in the panel as a row of five counts.

- **Production.** For each resource owed on a roll: if the bank holds enough, everyone is paid. If not, and exactly one player is owed that resource, they take what's left. If two or more are owed it, nobody gets it. The log says "Bank is out of <resource>." when that happens.
- **Setup payout** uses the same rule (it can never run out in practice).
- **Bank trade, harbour trade, Bumper harvest** can't take a resource the bank doesn't hold. Those choices are disabled in the UI and absent from `legalMoves`.
- Payments for builds and cards, and discards, return to the bank. Steals, Corner the market and player trades move cards between hands only.

### 5.4 Piece limits

5 settlements, 4 cities, 15 roads per player. A city upgrade frees a settlement piece. `legalMoves` omits a build when no piece is left; the build button shows "N left" and is disabled at 0. Road crew ends early when no road piece or no legal edge remains, with the log "No roads left to build." or "No room for new roads." as appropriate. Setup placements count against the limits.

### 5.5 Smaller alignments with the spec

- The discard choice is a `Move`, so the AI and the test runner use it the same way as the UI.
- Win check runs after every `apply` that can change points and at the start of every turn, exactly as the spec says. Only the current player can win.
- "Preview win" stays, Debug builds only.

## 6. AI

### 6.1 Interface

```swift
struct PlayerView: Codable {                 // built by Engine.view(state, for: seat)
    var me: Int
    var hand: [Resource: Int]
    var devCards: [DevCard]
    var opponents: [OpponentSummary]         // seat, card count, dev card count, knights, road length, public points
    var board: BoardSnapshot                 // tiles, corners, edges, harbours, robber, owners
    var bank: [Resource: Int]
    var dice: [Int]?
    var deckCount: Int
    var awards, phase, turn, firstPlayer, current
}

protocol Opponent {
    func chooseMove(view: PlayerView, legal: [Move]) async -> Move
    func respondToTrade(_ offer: TradeOffer, view: PlayerView) async -> TradeResponse
}
```

The engine builds `PlayerView`, so the redaction cannot be skipped. The guarantee, precisely: no public function in `SaltmarshAI` accepts a `GameState`, the view model only ever passes `PlayerView` values to an `Opponent`, and the only `GameState` values inside the AI target are the guessed ones returned by `Engine.sampleFullState(from:using:)`. A test asserts the first two by inspection of the API and the third by checking that every opponent hand in a sampled state differs from a seeded real state in at least one game (sampling cannot reproduce hidden cards it was never given).

### 6.2 Heuristic policy (the base layer)

Deterministic given the view and a seed. Implements the spec's section 6.1 and adds:

- **Setup:** best corner by spot score (pips, plus a bonus per resource the player doesn't yet produce, plus a harbour bonus when it matches a resource they produce well). Setup road points toward the best remaining corner within two edges.
- **Main phase priority:** city, settlement on best reachable corner, road toward the best unowned legal corner, buy a dev card, trade (player offer first if a 1:1 or 2:1 swap of surplus for a missing resource completes a build this turn, else harbour, else bank), end turn.
- **Robber:** the tile that costs the points leader the most pips without touching the AI's own corners; prefers tiles whose owners hold cards.
- **Victim:** the candidate with the most cards; ties go to the points leader.
- **Discard:** keep what completes the nearest build; discard from the largest surplus.
- **Cards:** as the spec's section 6.1 card play list.
- **Trade responses:** accept if the evaluator says the trade improves its own position by more than a small threshold; counter when a one-card tweak would; else decline. Captain and Admiral also subtract the proposer's gain.
- **Trade proposals:** only when a swap would complete a build this turn.

### 6.3 Rollout search (the top layer)

For a real decision (setup corner, setup road, which main action, robber tile, discard, trade response, whether to execute a trade), with more than one candidate:

1. **Determinize.** Ask `Engine.sampleFullState(from: view, using: &aiRNG)` for a guessed full state: each opponent gets a random hand of the right size (weighted by what their corners produce), unknown dev cards are dealt from the remaining deck composition, the remaining deck is shuffled. Repeat for several samples.
2. **Play out.** For each candidate move and each sample, apply the move to the guessed state, then let the heuristic policy play every seat for D rounds using the real engine (dice included).
3. **Evaluate** the end position for the AI's seat: public points × 10, plus hidden VP cards, plus production pips weighted by how much each resource is still needed, plus a diversity bonus, plus proximity to each award, minus a penalty for holding more than 7 cards. Score is own evaluation minus the best opponent's.
4. **Pick** the candidate with the best mean. Ties go to the heuristic's own choice.

Budget is a count of playouts plus a wall-clock cap. Tests use count-only budgets so results are reproducible from a seed. Rolling, single-candidate steps, and forced moves skip the search entirely.

### 6.4 Effort levels

One dial, five stops. Exact numbers are tuned by the builder to the time caps; the shape is fixed.

| Level | Base policy | Blunders | Robber | Trades | Search |
|---|---|---|---|---|---|
| Deckhand | yes | picks a random legal move about a third of the time | random tile not its own | never offers; declines all | none |
| Sailor | yes | about one move in eight | richest tile | accepts only clear gains | none |
| Mate | yes | none | targets the leader | full heuristic trading | none |
| Captain | yes | none | leader | full, weighs proposer's gain | a few hundred playouts, ~0.75 s cap |
| Admiral | yes | none | leader | full, weighs proposer's gain | a few thousand playouts, ~1.5 s cap |

The dial must measurably matter: in seeded two-player matches, Admiral must beat Deckhand in at least 70% of games, and each level should beat the one below it more often than not. This is checked two ways (section 8): a fast `swift test` case at reduced search budgets proves the dial has an effect at all, and the `ai-bench` executable runs the shipped budgets and prints the full level-versus-level matrix. The AI is not done until the benchmark meets the criterion.

### 6.5 Safety net

If an `Opponent` returns a move that isn't in the legal list, the view model substitutes the heuristic's move; if that fails too, the first legal move. A game with an always-wrong opponent must still finish. If the search exceeds its cap, it returns the best so far or the heuristic's choice.

### 6.6 Pacing

AI actions apply one at a time with a short pause (about half a second) so the human can watch the board and the log. The pause is injected through `TurnRunner`, so tests run at zero delay. During an AI turn the human's controls are disabled, with the status line reading "<Name> is thinking…". Reduce Motion does not remove the pause (it is for comprehension, not decoration).

**What the panel shows during an AI turn.** The header and status name the AI. The hand area shows the hand of the single human seat when there is exactly one human; with two or more humans it shows no hand. An AI's hidden victory points are never shown as "+N". Where every opponent is an AI, no pass-the-device prompts ever appear.

**Resuming a saved game** whose current seat is an AI restarts that seat's turn from its current phase on launch.

## 7. Screens

Everything from the spec's section 5 panel list, plus:

**New game sheet.** Player count (2 to 4). One row per seat: colour dot, fixed name, a Human/AI segmented control, and for AI an effort picker with the five names and a one-line description each. "Start game". Defaults: 3 players, Crimson human, the rest Mate.

**Order strip** (section 5.1), shown during the first roll and setup only.

**Bank row**: five resource counts, placed above the trade sections.

**Trade with players** section, below "Trade with bank": offer builder, target picker, Offer button; after an offer, the responses list and Trade/Withdraw buttons. The human responder prompt takes over the panel like the discard box does.

**Build buttons** carry "N left".

**Pass-and-play.** As in the prototype, the panel switches to whoever must act next (roller, discarder, trade responder) with the status line naming them. No extra interstitial screen (my call, keeps parity with the feature file).

**Autosave.** The current game is saved after every applied move through the `GameStore` protocol; the app's store writes to Application Support. On launch, a saved game resumes; "New game" overwrites it. Save format is the `Codable` `GameState` (which already carries the seat controllers).

## 8. Testing

**Gherkin runner** (Swift Testing, in `GherkinTests`): a parser for Feature, Rule, Background (feature and rule level), Scenario, Scenario Outline with Examples, data tables, tags, comments. Scenarios become parameterised `@Test` cases so each reports on its own. Steps are regex-matched Swift closures; an unmatched step fails that scenario and lists the missing step text. Steps drive `GameViewModel` (zero pacing, in-memory store, seeded engine) and assert on `ScreenState`. Scenarios that need a specific board, hand or dice result set it up through test-only engine helpers (seeded boards, direct hand assignment, forced next roll) rather than through the UI.

**`ScreenState` is a render model, not pixels.** It exposes by label every string and enabled state the feature file names ("Roll dice", "Discard 4 cards", "Steal from Cobalt", header text, status text, hand counts, harbour rows, scoreboard rows, victory card contents) and every piece of render intent the views draw from: which corners glow, which edges are dashed, which tiles are selectable, which number discs are marked hot (6 and 8) or hit (matched the roll), which buildings are steal targets, which pieces are the champion's, the robber's tile, the victory animation mode (full or reduced) and the confetti schedule. A visual scenario therefore asserts on intent ("the 6 and 8 discs are marked hot", "the confetti schedule has a centre burst, two corner cannons and a second wave 0.55 s later"); the views are the only thing that turns intent into drawing.

**Every scenario runs somewhere.** Scenarios that can only be checked against a running app (overlay hidden at launch, Reduce Motion, launch flow) carry a `@ui` tag; the Gherkin runner skips those and `AppUITests` implements them by hand with the same wording in test names. There are expected to be fewer than ten.

**Engine tests:** the spec's section 7 checklist as unit tests; 1,000 generated boards pass all balancing rules; 1,000 seeded heuristic-vs-heuristic games finish with the invariants from `tests/playgame.py` holding after every move (no negative hands, distance rule, connectivity, valid award holders, 25 dev cards, bank plus hands equal 19 per resource, piece limits never exceeded).

**AI tests (`swift test`, fast):** always-invalid opponent finishes a game; search is deterministic with a count budget; the redaction guarantee from section 6.1; dial effect at reduced budgets: Mate beats Deckhand and a small-budget Captain beats Mate, each in at least 65% of 40 seeded two-player games.

**AI benchmark (`swift run ai-bench`, opt-in, minutes to hours):** the full five-by-five win matrix at shipped budgets over a configurable number of seeded games. The 70% Admiral-versus-Deckhand criterion and the "each level beats the one below" criterion are judged here, and the result table is pasted into the spec.

**UI tests (XCUITest):** app launches on macOS and on an iPhone simulator; the `@ui` scenarios above.
